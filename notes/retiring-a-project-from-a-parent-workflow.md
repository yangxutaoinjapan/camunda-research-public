# Retiring a project from a parent workflow

## Problem

A delivery workflow was built so that every governed project had its own
message-start entry into one shared parent workflow. Adding a project was a
well-trodden path. Removing one, after the product behind it was retired, turned
out to have no path at all: the clean-up could not be finished without
redeploying the engine, and the engine was not highly available.

The question is how to design the registry, the process definitions and the
identities so that removing a project is as small a change as adding one.

## What we observed

Per-project start events and numbered elements. The parent definition held one
set of elements per project: a message start, a reservation task, a duplicate
gateway, a call activity, completion and failure tasks, three end events and
the connecting flows, about nineteen elements plus their diagram shapes. The
identifiers were numbered by the position of the project in a policy file
(`Start1`, `Start2`, and so on). A checker matched the n-th policy entry with
the n-th set of elements.

Position-based naming turned a deletion into a renumbering. Removing the sixth
of seventeen entries required renaming every element of the following eleven
sets: 972 identifier occurrences in one definition. A script did it, and the
model validator still passed afterwards, which shows the numbering carried no
meaning beyond the checker's own convention.

Hard-coded counts. The policy checker compared the generated client map with
"exactly eight message routes" as a literal. Seven routes failed it. The check
exists to prove that every route is present, not that there are eight of them.

Generated copies. The deployment manifest embeds a rendered copy of the
definitions, and a front-end schema file is derived from the policy. A source
change therefore produced a diff of several thousand lines, almost all of it
generated.

A dozen places per project. Besides the definitions: a registry row, a secret
projection holding a read-only repository token, an init container that clones
the project's GitOps source, an environment variable naming the clone, the
list of Argo CD applications the worker may patch, the notification
application list, a rule in a decision table, and per-project identities (a
broker client, a publisher secret path, a Git account).

Grants live in start-up configuration. The engine's identity configuration
listed every client and every per-message grant as start-up environment
variables, generated by a bootstrap script. The policy checker required the
policy and that configuration to agree, so deleting the policy entry meant
editing the engine's start-up configuration, which restarts the engine. The
clients and grants cannot be removed by editing a policy file alone.

Prior retirements had left traces. An earlier product replacement reused the old
product's start event for the new product, and a later commit had to retire a
stale publisher grant. Both are signs that renaming and deleting were
avoided because they were expensive.

The retirement of the product's runtime objects (workload, routes, listener,
database) was straightforward and used existing runbooks. Only the governance
definitions had no retirement path.

## What works

Treat the registry as the only place a project is described, and generate
everything else from it. A registry row lists the key, repository, application,
namespace and deployments. Clients, grants, secret projections, clone
containers, environment variables, allow-lists and decision-table entries are
produced by a generator and committed. Retiring a project is deleting its row
and regenerating.

Name by key, not by position. Elements named after the project key
(`Start_<key>`) can be removed without touching their neighbours. Checkers
should compare sets derived from the registry, never literals such as the
current number of projects.

Keep the number of project-specific definition elements at zero where the
engine allows it. One message start plus a lookup of the target from the message
name or a variable keeps the parent identical for every project; adding or
removing a project then changes data, not the process model.

Move grants out of start-up configuration. Reconcile clients and authorizations
through the engine's identity API from the same registry, and keep the start-up
configuration to the few identities needed before the API is reachable. Then a
retirement revokes grants without a restart.

Give retirement its own runbook, with read-back. It should cover the registry,
the grants, the secret paths, the Git account and the broker client in one
approved change and verify each absence, in the way creation already does.

## What we did not verify

- The proposed design was not implemented in the observed environment. The
  migration order and the cost of each step are estimates.
- We did not test whether reconciling clients and authorizations through the
  identity API covers every grant type used here on the tested engine version
  (Camunda 8.10).
- We did not measure how long a start-up configuration change interrupts the
  engine; it was avoided rather than timed.
- A single message start with lookup may change how correlation keys and
  per-project permissions are expressed; the effect on duplicate handling was
  not exercised.
